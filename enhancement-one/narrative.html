Artifact Overview

For Enhancement One, I selected the Travlr Getaways full-stack web application that I originally developed as my CS 465 final project during summer 2026. The artifact uses a MongoDB, Express, Angular, and Node.js architecture and includes a public travel site and an administrator application. I selected this artifact because it represents a complete software system rather than an isolated exercise. It gave me the opportunity to demonstrate front-end development, server-side validation, API design, database integration, authentication, authorization, testing, and communication with both customers and staff users.

The original artifact allowed an authenticated administrator to add, edit, and delete trips. It demonstrated basic CRUD functionality, but it did not provide customers with a structured way to search the catalog or ask a question about a specific trip. The original implementation also did not provide enough evidence that monetary values were stored exactly, that authorization was checked against a user’s current role, or that failure paths were handled safely. My enhancement moved the application beyond basic functionality by creating a more complete and secure customer-to-staff workflow.

Reason for Selecting the Artifact

I chose Travlr Getaways because it connects directly to my goal of becoming a software engineer. It shows how several parts of a production-style application work together and how a change in one layer affects the others. For example, adding customer inquiries required changes to the public interface, routes, controllers, validation utilities, database models, the protected Angular administrator interface, and automated tests. This made the artifact appropriate for demonstrating software design and engineering rather than only visual changes.

The artifact also allowed me to respond directly to instructor feedback. The feedback asked for specific implementation evidence, exact validation rules, an explanation of authentication and API security, before-and-after examples, test results, and clear design decisions and trade-offs. The following sections explain what I implemented and connect each claim to evidence in the appendix.

Implemented Enhancements

Trip Search, Filtering, and Sorting

I added a public search interface that allows customers to search by trip name or resort, set inclusive minimum and maximum prices, select a departure-date range, and choose an allowlisted sort order. Search text is limited to one scalar value of no more than 100 characters. Regular-expression metacharacters are escaped so text such as an asterisk is treated literally instead of becoming an executable pattern. Date filters accept real YYYY-MM-DD calendar dates, require the ending date to be on or after the starting date, and include the entire ending day. Price and date filters can be combined, and the form retains the customer’s choices after submission. Every allowed sort includes MongoDB _id as a unique tie-breaker so repeated requests return a stable order.

Exact Price Handling

I replaced permissive price handling with an exact monetary contract. A trip price must be a finite JSON number from 0 through 999,999,999.99 and may contain no more than two decimal places. Blank values, booleans, currency symbols, grouped strings, excessive decimal places, and out-of-range values are rejected before database access. Valid values are stored as MongoDB Decimal128 and serialized as numeric JSON values for the application. This design prevents silent rounding and binary floating-point errors while preserving correct numeric sorting and filtering.

Customer Inquiry Workflow

I added an inquiry action to each public trip. The form displays the selected trip and clearly explains that the submission is an inquiry rather than a booking. A successful submission creates a New inquiry, generates a customer reference number, and redirects to a confirmation page protected by a signed, short-lived receipt. The confirmation does not expose a MongoDB identifier and cannot be opened by simply guessing another customer’s reference number.

Staff Inquiry Workflow

Authenticated staff can open a protected inquiry inbox, review customer questions, filter them by status, move through paginated results, and update an inquiry to New, In progress, or Closed. The status controller accepts only the status field. It cannot be used to overwrite the customer’s name, email, message, trip, or reference number. This produces a useful operational workflow while limiting the authority of each request.

Authentication, Authorization, and Safe Failure Handling

The application treats authentication and authorization as separate decisions. JWT middleware first authenticates the requester. Staff-only middleware then retrieves the account from MongoDB and checks its current role before a protected inquiry read, trip mutation, or status update is allowed. Checking the database on every protected request means a revoked staff role stops working immediately, even when the user still has a previously issued token. Public registration always creates a customer account, so a client cannot assign itself a staff role by including one in the request.

I also limited error exposure. Invalid inputs return bounded field messages, while database failures return generic responses rather than raw queries, connection details, or stack traces. Legacy trip descriptions are sanitized so only paragraph markup is retained. These decisions protect customer data and reduce the opportunity for malformed input to change application behavior.

Screenshots demonstrate the user-visible workflow, while unit and integration tests verify behaviors that are difficult to prove visually, including Decimal128 storage, rejection before database access, safe failures, role revocation, and authorization boundaries. All suites passed during final verification on October 10 and 11, 2026. Design Decisions and Trade-Offs

I selected Decimal128 instead of binary floating-point storage because prices must retain exact cents during sorting, filtering, and updates. This required conversion logic at the database and API boundaries, but it prevents silent precision loss and makes the stored representation match the meaning of the field.

I preserved the existing server-rendered customer site and expanded the Angular administrator application. This reduced migration risk and respected the original architecture while establishing clear public and staff responsibilities. The trade-off is that two interfaces must be maintained and tested, which I addressed with backend, integration, and Angular test suites.

I used a signed, short-lived receipt for confirmation instead of exposing database identifiers. I also chose to check the current database role on every staff request instead of trusting only a role recorded in an older token. These decisions add a small amount of processing and implementation complexity, but they reduce information exposure and ensure that removed privileges stop working immediately.

The application uses browser validation for immediate guidance and repeats the rules on the server. This duplicates some validation logic, but the duplication is intentional: browser messages help nontechnical customers correct mistakes, while server validation protects the system from modified clients and direct API requests.

Connection to the Computer Science Program Outcomes

Course Outcome 1: Collaboration and Decision-Making

This enhancement supports collaboration by presenting the same workflow in forms appropriate for different audiences. Customers receive plain-language search controls, validation feedback, and a reference number. Staff receive an organized inbox, status filters, and explicit save actions that support consistent decisions. Technical collaborators receive the validation contract, endpoint behavior, design trade-offs, and test evidence needed to review or maintain the system. By connecting customer questions to staff decisions without exposing internal identifiers, the solution helps technical and nontechnical users contribute to one shared process.

Course Outcome 2: Professional Communication

I used written, visual, and technical communication throughout the enhancement. The public pages explain the purpose and limits of the inquiry process, the administrator interface explains when a status change takes effect, and the evidence appendix shows observable results. This narrative and the revised design document communicate the architecture, validation rules, security decisions, and test outcomes in language that can be understood by an instructor, developer, employer, or nontechnical stakeholder.

Course Outcome 3: Computing Solutions and Algorithmic Principles

The search feature demonstrates the design and evaluation of a computing solution with explicit constraints. It constructs database queries only from validated, allowlisted inputs; combines text, price, and date criteria; escapes regex characters; and produces deterministic results with a unique tie-breaker. The design uses database-side filtering and sorting instead of retrieving the entire collection and sorting it in application memory. That choice scales with the database query engine and avoids unnecessary transfer and processing. I evaluated the solution through combined-filter, empty-result, invalid-input, safe-failure, and numeric-order integration tests.

Course Outcome 4: Techniques, Skills, and Tools

The enhancement applies full-stack development skills across Express controllers and middleware, Mongoose schemas and Decimal128 data, Handlebars pages, Angular components and services, JWT authentication, role-based authorization, and automated tests. I used these tools to deliver business value: customers can find relevant trips and request information, while staff can manage the resulting work in a controlled interface. Centralized validation and repeatable tests also make future maintenance safer.

Course Outcome 5: Security Mindset

I anticipated how malformed input, stale permissions, mass assignment, unsafe error messages, regular-expression characters, and exposed identifiers could be abused. I mitigated those risks through strict server validation, allowlisted fields and sort values, literal search handling, current-role authorization, signed confirmation receipts, sanitized descriptions, and generic failure responses. Negative-path tests verify not only that valid users succeed but also that unauthenticated, unauthorized, invalid, and revoked requests fail safely.

Reflection

Enhancing this artifact helped me understand that software engineering is not complete when a feature works once on the screen. A maintainable solution needs an explicit data contract, protected trust boundaries, predictable failure behavior, and evidence that the important paths continue to work. The most valuable part of this enhancement was connecting user-visible behavior to server rules and automated verification.

I also learned that documentation is part of implementation. My original work showed functionality, but it did not make every design decision easy to evaluate. By documenting exact rules, security responsibilities, test outcomes, and trade-offs, I can now explain why the solution is reliable and how another developer could continue the work. The final artifact better represents the quality of work I want to present to employers after graduation.
